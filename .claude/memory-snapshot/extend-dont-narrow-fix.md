Пользователь повторял это много раз, и я много раз нарушал: **нельзя чинить скрипт под конкретный
сломанный сайт**. Каждый новый баг должен ДОПОЛНЯТЬ общую логику очистки так, чтобы покрылся класс
проблемы и при этом ничего не сломалось на остальных.

**Why:** подгонка под один сайт систематически ломает соседние. Живые примеры из одной сессии:
ослабил распознавание меню, чтобы найти меню sylhet, — и пара CTA-кнопок из hero-баннера стала
хедером на gigaworks, залезла внутрь `<main>`, настоящее меню из 6 пунктов пропало. Добавил
вынимание футера из блока комментариев ради sanjhapunjab — `<main>` упал с 58% до 3%. Ослабление
ради одного сайта = регресс на другом, и так по кругу. Плюс регресс-набор покрывает только те сайты,
что уже есть (11 штук), а пользователь берёт новые домены пачками — значит на новом архиве всё
повторяется.

**How to apply:**
1. Найдя баг, сначала сформулировать КЛАСС («секции ищутся только среди прямых детей body»), а не
   симптом («у sanjhapunjab выкосилось меню»). Симптом почти всегда в другом месте, чем корень.
2. На каждую правку писать ОТРИЦАТЕЛЬНЫЙ тест: что НЕ должно сработать. Ослабление правила без
   отрицательного теста — это будущий регресс.
3. Гарантии зашивать в контракт на результат (`verify_output_contract`), который проверяется на
   КАЖДОЙ странице, а не в регресс-набор: контракт защищает и те архивы, которых я не видел.
4. После правки общей логики — полный регресс по всем сайтам с сырым `.bak`. Утверждать «ничего не
   сломалось» без прогона нельзя.
5. Классы дефектов, невидимые на текущем наборе, искать ревью-агентами — см. [[cleaner-code-review]].

Связано: [[fix-script-not-file-restart-server]] (чинить скрипт, а не выходной файл).
