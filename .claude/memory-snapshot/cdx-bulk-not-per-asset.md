**Главный источник МЕДЛЕННОЙ очистки — CDX-поиски.** `web.archive.org/cdx/search` это ТЯЖЁЛЫЙ
запрос (легально 15-20с, под троттлом 40-60с), а `recover_asset_bytes` делал его ПО КАЖДОМУ
невосстановленному ассету. Страница с десятком таких ассетов = десяток CDX подряд = минуты-получас
(longandshort: 190-220с, из них 6+ CDX по 20-60с).

**Три рычага (2026-07-22), очистка 190с → ~30с:**
1. **Ленивый CDX.** `recover_asset_bytes` строил ОБА кандидата сразу (прямой id_-fetch + CDX), и CDX
   дёргался даже когда прямой успешен. Стало: прямой fetch по ts ПЕРВЫМ, CDX только при неудаче.
2. **ts из оригинала + ts страницы.** `_wb_ts(url)` достаёт ts из wayback-обёртки; `_RUN_SITE_TS` —
   ts захвата всей страницы как фолбэк для «голых» абсолютных ссылок того же домена (ассет снят
   вместе со страницей). `localize_media_refs` теперь передаёт ts. Прямой fetch по ts вместо CDX.
3. **BULK-CDX по домену.** `_domain_cdx_map` — ОДИН префиксный запрос `domain/*` (333 строки за 2.5с)
   строит {url: ts} на весь сайт, дальше поиск ассета — локальная выборка без сети. Заменяет N
   медленных CDX одним. Лок держится НА ВРЕМЯ запроса (иначе гонка → 4 одинаковых запроса). Ассета
   нет в карте → мгновенно None, без per-URL CDX. При сбое запроса — откат на поиск по одному URL.

**Ничего не отключено:** восстановление то же, просто без лишних CDX. `id_` требует ТОЧНЫЙ ts (не
редиректит), поэтому фолбэк по ts страницы срабатывает не всегда — тогда bulk-карта. Троттл МОЕГО IP
раздувал замеры (весь день молотил архив); у пользователя на свежем IP CDX ~2-5с.
