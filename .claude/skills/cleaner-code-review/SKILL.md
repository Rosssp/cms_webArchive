# Ревью-заход по чистильщику

## Зачем это есть

История проекта: правки писались **по симптомам**. «Меню выкосилось» → патчили меню. Настоящая
причина лежала через два файла (секции искались только среди прямых детей `body`, поэтому на
обычном `<body><div id="wrapper">` получалась ОДНА секция, и меню обрезалось за ненадобностью).
Симптом лечили неделю, корень стоял нетронутым.

Три параллельных ревью-агента нашли **29 таких корней за пять минут**, включая тот самый — и ещё
один, который на тестовых сайтах не проявляется вообще, но выстрелил бы на первом же современном
WordPress (сужение области поиска до `<main>`, который пришёл из архива → второй `<header>` посреди
статьи → удаление ссылок статьи как «пунктов меню»).

Вывод: глазами эти классы не ловятся, потому что они не видны на текущем наборе сайтов. Ревью
агентами окупается и должно повторяться, а не быть разовой акцией.

## Когда запускать

- после любой правки порядка проходов в `clean_html_file` или `auto_link_menu`;
- после изменений в сборке лендмарков (`_promote_header`, `_promote_footer`, `ensure_landmarks`,
  `plan_layout`, `assemble_main_from_plan`, `verify_landmark_roles`);
- после добавления нового вызова модели в `semantics.py`;
- когда «на новом архиве опять криво», а по симптому причина не находится.

## Как запускать

Три агента ПАРАЛЛЕЛЬНО (одним сообщением, тип `Explore`), каждый на СВОЙ класс дефектов. Не сливать
в одного: общий промпт даёт поверхностный обзор вместо глубокого разбора одного класса.

Каждому агенту обязательно дать:
1. полные пути к файлам (`clean_wayback_site.py`, `site_studio/site_edit.py`, `site_studio/semantics.py`);
2. **реальные примеры уже случившихся багов этого класса** — это главное, что делает отчёт полезным:
   агент ищет ту же форму дефекта, а не «что-нибудь подозрительное»;
3. требование указывать файл, строку, конкретный сценарий отказа и ЧТО УВИДИТ пользователь;
4. запрет чинить и запрет на стилистические замечания;
5. требование честно помечать неуверенные находки и писать, чем их подтвердить.

### Класс 1 — перезапись решений между проходами
Поздний проход молча отменяет то, что ранний сделал правильно.
Примеры из истории: корректор ролей переименовывал блок в `<main>` ПОСЛЕ правильной сборки, и его
кандидаты ограничены 4000 символами, поэтому он мог выбрать только мелкий блок (`<main>` = 3%
страницы); ветка сборки пропускалась из-за `if soup.find("main") is None`, потому что `<main>` уже
создал предыдущий ИИ-проход; поиск хедера сужался до `<main>`, а хедер лежал снаружи.

### Класс 2 — слишком узкая область поиска
Лукап не находит то, что в документе ЕСТЬ.
Примеры: `find_all(recursive=False)` там, где цель законно вложена; срезы `[:6]`, `[-4:]`; спуск в
обёртку только при единственном ребёнке; требование CSS-класса там, где в реальной вёрстке его нет;
пороги вида «текст > 4000 → пропустить», отсекающие правильный элемент.

### Класс 3 — ответ модели применён без проверки
Примеры: модель пометила ДВА блока как `header`, взяли первый — пустой `<div>`; вернула `null` для
роли, и страница ПОТЕРЯЛА футер, который у неё был; пометила футером блок, в котором лежит вся
страница; локализованная строка копирайта без `©` не распознаётся при повторной очистке и
дописывается второй раз.

## Что делать с отчётом

1. Чинить по убыванию **вероятности выстрелить на реальном архиве**, а не по красоте находки.
2. На КАЖДУЮ правку — отрицательный тест (что НЕ должно сработать), иначе фикс одного случая ломает
   соседний. В этом проекте это происходило многократно.
3. Прогнать регресс по сайтам с сырым `.bak` и сверить: лендмарки, доля текста в `<main>`, число
   пунктов меню, число секций, уровни заголовков. Одной цифры «футер есть» НЕДОСТАТОЧНО — однажды
   этим «футером» оказалась off-canvas панель.
4. Находки, которые не чинишь, — записать в `docs/CLEANER.md`, иначе они потеряются.
